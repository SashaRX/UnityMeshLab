# Reverse query backend integration — 2026-10-14

Branch `codex/transfer-performance`, source base `97d8828f`. This continues the
same transfer performance experiment. The typed backend is connected to the
ordinary Reverse workflow. Measurements used private native builds without
changing package binaries, FBX or user scenes. PR publication rebuilds the normal
xatlas plugins through native CI; the optional Intel runtimes remain unpublished.

## Selection and retained behavior

`ReverseUvTransfer.Options` defaults to Auto. Batches with at least 512 pending
centres and at least 1,024 donor faces may use the optional Embree backend.
Missing/older libraries and donor sets over 200,000 faces keep the managed path.
Legacy explicitly disables batching for the paired reference. The private test
binding is scoped to its DLL owner, with all scenes disposed before unload.

Reverse searches individual charts. The first integration tried batching each
chart separately, but real islands were mostly too small to use Embree. The
accepted path builds one donor tree and discovers candidates at the complete
projection reach. Candidate IDs are partitioned back into original charts;
each chart's `TriangleBvh` partition, leaf order and managed primitive tests
select its nearest face. A globally closest proposal cannot truncate another
chart's possible anchor. Native arithmetic never supplies the final face,
weights, point or UV.

Only independent centre nearest queries are precomputed. Chart-bound checks,
ambiguity scans, work-budget increments, corners, interior/coverage probes,
whole-island grouping, overlap policy, repair, final packing and publication
audits execute in their original order. No triangle or UV seam is generated by
the backend. Candidate overflow discards the entire centre's cache and repeats
the original queries; native failure similarly discards the complete batch.

## Ownership and bounds

Each `ProjectFaces` call owns one native scene and fixed arrays for up to 4,096
centres, 256 candidates per centre and eight workers. Queries, counts, candidate
IDs, sparse chart answers and worker scratch are reused across target meshes and
face blocks. There is no retained model/LOD cache or static native scene. Normal
completion, exceptions and cancellation dispose the native owner. A fresh LOD
projection gets a fresh owner. The fixed sparse answer/candidate tables occupy
about 36 MiB; scene, source and managed BVH metadata are additional bounded data.

`Native~/src/embree_queries.cpp` has a versioned ABI, pointer/index/input bounds,
RAII cleanup on creation failure and bounded worker creation with joined threads
on failure. Its optional CMake target is `meshlab-queries` with
`MESHLAB_EMBREE_QUERIES=ON`, `MESHLAB_EMBREE_ROOT=<pinned 4.3.3 distribution>` and
`MESHLAB_COPY_PLUGINS=OFF`. Normal builds remain dependency-free. Runtime/license
publication must go through the native CI workflow; no private DLL is copied
into `Plugins/`.

## Verification and reproduction

The private project is `UnityMeshLab-transfer-bench-20261008`, Unity 6000.2.6f2,
Windows x64. Fixtures are Cafe_Table_A_01, Modern_Kitchen_A and Kamaz Typhoon
(`kamaz_Off.fbx`). Each process runs ordinary Transfer first and freezes its
complete outputs, then runs Reverse exclusive and Reverse overlap at 32 tex/m,
2 px padding and Fill atlas. Source geometry/assets remain unchanged.

`Tools~/run-reverse-query-benchmark.ps1` alternates Legacy and Auto order for
three independent processes per arm. Both arms use the same previously verified
oneTBB xatlas/search library, shared occupancy snapshots and witnessed Burst
rasterization; only the query backend differs. The first pair additionally runs
the complete transfer-performance/Reverse regression set and backend tests.

`Tools~/compare-transfer-performance.py` compares all 120 stable exports per run
against the immutable pre-integration baseline by exact numeric bits, including
geometry, UV, provenance, quality, atlas dimensions, input hashes/frames and
packing/search/audit counts. JSON decimal formatting differences alone do not
relax that gate. Full Reverse timing is `Reverse workflow total`, including input
cleanup and final layout validation; `Reverse total` is also recorded separately.
FBX export, benchmark-file writing and Unity startup/import are outside that time.

Backend tests retain per-chart nearest answers across two blocks, including a
nearer face in another chart; test exact hit bits, repeated scratch reuse,
whole-query capacity fallback, native-error fallback, cancellation and disposal.
The two C# compile variants and five native regressions are checked independently.

## Final full-workflow measurements

Three independent processes per arm, alternating order. Seconds below are the
medians of `Reverse workflow total`, including cleanup and final layout audits.
They are not query-only times.

| Model | Policy | Legacy (s) | Auto (s) | Change in elapsed time |
|---|---|---:|---:|---:|
| Cafe_Table_A_01 | exclusive | 0.773 | 0.749 | -3.1% |
| Cafe_Table_A_01 | overlap | 1.703 | 1.706 | +0.2% |
| Modern_Kitchen_A | exclusive | 6.167 | 6.188 | +0.4% |
| Modern_Kitchen_A | overlap | 6.285 | 6.244 | -0.6% |
| Kamaz Typhoon | exclusive | 16.178 | 16.471 | +1.8% |
| Kamaz Typhoon | overlap | 33.545 | 34.035 | +1.5% |

Cafe never selects Embree; its variation is not an accelerator gain. Kitchen
uses 9,246 centres and one scene/buffer set per policy; Kamaz uses 27,692 centres
and two scene/buffer sets per policy. Both exceed one 4,096-query block per owner,
so the real-model checks witness buffer reuse. Candidate overflows and native
failed batches are zero. All three candidate repetitions retain these counters.

Projection medians (Legacy / Auto), in milliseconds: Cafe 21.5 / 22.5 exclusive,
9.6 / 9.4 overlap; Kitchen 322.0 / 330.6 exclusive, 386.9 / 347.6 overlap; Kamaz
1,429.9 / 1,434.0 exclusive, 1,524.6 / 1,588.1 overlap. The large isolated-query
gain from the previous report does not carry over to complete Reverse: centres
are only part of projection, and final packing dominates the full workflow.
These three samples have meaningful variation (Kamaz Auto overlap spans
33.950–37.148s). There is no qualified full-workflow acceleration; the roughly
1–2% Kamaz median regression is recorded rather than hidden. Keep native runtime
publication experimental/OFF instead of promoting this as a default speed gain.

## Final evidence

All six final processes retain all 120 stable exports by exact numeric bits:
720 file comparisons, with unchanged geometry, UVs, provenance, inputs, atlas
dimensions, quality, work budgets, packing decisions and refusal order. There
are no JSON formatting differences in these final runs. Both expanded suites
pass **294/311**, fail zero and skip 17 optional cases. The other four processes
each execute and pass all three required model cases with no skips. Thus 36
complete Reverse workflows run across both policies/arms, plus ordinary Transfer
in every model case. Native regressions pass **5/5**; C# compile checks pass both
FBX define variants with zero errors. No guard or tolerance is relaxed.
